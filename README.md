# Peak-Hour Route Optimization: A Big Data Analytics Pipeline for UK Bus Transport

A PySpark-based predictive analytics pipeline that ingests BODS (Bus Open Data Service) timetable and vehicle-location data, processes it at scale, and forecasts peak-hour service patterns to support transport authority scheduling decisions.

## Project overview

This project builds a distributed data pipeline that:
- Ingests TransXChange timetable XML and SIRI-VM vehicle location XML from BODS
- Cleans and processes the data using PySpark DataFrames
- Stores processed data in SQLite with parameterised queries
- Trains and compares three classification models to predict peak-hour trips
- Produces visualisations and an architecture diagram to communicate findings

**Stakeholder:** Transport Authority / Urban Planner — using peak-hour trip forecasts to inform route scheduling and fleet allocation decisions.

## Data sources

| Dataset | Format | Source | Records |
|---|---|---|---|
| Timetable | TransXChange XML (zipped, per-operator) | [BODS](https://data.bus-data.dft.gov.uk/) | 1,184,667 |
| Vehicle location | SIRI-VM XML | [BODS](https://data.bus-data.dft.gov.uk/) | 26,193 |

Combined dataset exceeds the 100,000-record Big Data Scale Requirement.

## SparkSession configuration

```python
import os, sys
os.environ["PYSPARK_PYTHON"] = sys.executable
os.environ["PYSPARK_DRIVER_PYTHON"] = sys.executable
os.environ["SPARK_LOCAL_IP"] = "127.0.0.1"

from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .appName("RouteOptimization") \
    .master("local[*]") \
    .config("spark.driver.host", "127.0.0.1") \
    .config("spark.driver.bindAddress", "127.0.0.1") \
    .config("spark.sql.shuffle.partitions", "8") \
    .config("spark.driver.memory", "4g") \
    .getOrCreate()
```

**Notes on configuration:**
- `SPARK_LOCAL_IP` and `driver.bindAddress` are pinned to `127.0.0.1` to avoid socket connection errors caused by multiple network adapters on Windows.
- `spark.sql.shuffle.partitions` is set to 8, exceeding the minimum 4-partition requirement.
- `driver.memory` is increased to 4g to comfortably handle the 1.18M-row dataset.

## Pipeline stages

1. **Ingestion** — Extract 503 ZIP archives, parse 21,374 TransXChange XML files and 1 SIRI-VM XML file using Python's `xml.etree.ElementTree`, with per-file error handling and logging.
2. **Persistence checkpoint** — Parsed records are written to CSV (`timetable_parsed.csv`, `siri_parsed.csv`) immediately after parsing, so the expensive XML parsing step never needs to be repeated.
3. **Processing** — CSVs are loaded into PySpark DataFrames, repartitioned to 8 partitions, and cached. Nulls are profiled, types are cast, and `departure_hour` / `is_peak` features are engineered.
4. **Storage** — A representative sample (200,000 rows) is written to a SQLite database (`route_optimization.db`) using parameterised `INSERT` and `SELECT` statements to prevent SQL injection.
5. **Modelling** — Three classification models (Logistic Regression, Random Forest, GBTClassifier) are trained via a PySpark MLlib `Pipeline` (StringIndexer → OneHotEncoder → VectorAssembler → classifier) to predict whether a trip departs during peak hours, and compared on Accuracy, Precision, Recall, F1, ROC-AUC, and training time.
6. **Evaluation & visualisation** — Statistical profiling (mean, std, skewness, kurtosis) and four charts (hourly trip distribution, top operators, peak/off-peak split, GPS scatter) are generated with matplotlib/seaborn from Spark-aggregated data.

## Known data limitation

Timetable operator identifiers (TransXChange NOC-style codes, e.g. `OId_LU`) and SIRI-VM operator codes (e.g. `TFLO`, `BNML`) use incompatible naming schemes, and route/line numbers are reused across unrelated operators. A naive join on line number alone produced over 120 million spurious rows. Record-level joining between the two datasets was therefore not pursued; each dataset is analysed independently, and this is documented as a data integration limitation rather than resolved with an unreliable join.
